Product Design

Kredo

Kredo brings core freelance operations into one workspace. The current app includes client and request flows, proposal management, project tracking, billable time, expenses and invoice status. Instead of jumping between separate tools, a freelancer can follow work from a new client request through delivery and payment follow-up.

Open KredoView complete Kredo Figma UIView source code

Problem space

Freelancers often handle client details, proposals, project work, time, expenses and payment reminders in separate places. That makes it harder to see what needs action and what has already been billed or paid.

Design approach

I structured the workspace around recurring freelance tasks and put key areas in one navigation system. The dashboard brings clients, projects, proposals and billing into view, with time tracking and invoice actions nearby. The invoice table makes status and due dates visible so pending, partial and overdue invoices can be followed up.

Key design decisions

  • Keep clients, proposals, projects, time, expenses and invoices in one workspace navigation.
  • Show client and project counts alongside billing status to connect delivery with money owed.
  • Make time tracking visible on the dashboard so billable work is easier to record.
  • Use explicit invoice states such as sent, paid, partial and overdue to support clear follow-up.
  • Treat payment confirmation, duplicate submissions and partial payment as states that need verification, not just polished success screens.

Product screens

This separate Figma file contains editable Kredo screens built from the actual repository routes and UI patterns. Client names, amounts, counts and invoice rows are sample interface data, not real revenue or client results.

What I would validate next

I would test the flow with working freelancers from a new client request through proposal acceptance, project work, invoicing and payment confirmation. Important edge cases include partial payments, late invoices, timer interruptions, expense corrections, duplicate submissions and payment-webhook delays. Real payment success rates or time saved should not be claimed without evidence.

What I chose not to ship yet

The case study focuses on the workflow and product UI. Payment provider paths and invoice states should be validated in a test environment before claiming a production-verified payment experience.
